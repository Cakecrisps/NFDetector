Архитектура и порядок обработки¶

Поток данных¶

Агент: dumpcap → закрытый PCAPNG → manifest/spool
                       │ HTTPS :443 + индивидуальный ключ
                       ▼
                      LB (TLS)
                       │ HTTP api:8000, Docker backend
                       ▼
               API → PCAP volume + PostgreSQL
                       │ очередь файлов
                       ▼
                N parser-worker
                       │ отсортированные JSONL-артефакты
                       ▼
                detector-worker
         слияние потоков домена → TCP/IP reassembly
                  → окна правил → инциденты
                       │ одна транзакция
                       ▼
         checkpoint + курсоры + сигналы + outbox
                       │
                       ▼
                    Веб-панель

LB публикует единственный HTTPS-порт. API, workers и PostgreSQL общаются в закрытой Docker-сети backend; файлы читают из общего volume data. Worker не обращается к внешнему адресу панели. Сертификат находится на LB. Текущий Compose рассчитан на один Docker-хост.

Почему атака не теряется между двумя файлами¶

Parser выполняет только разбор файла. Он не решает, что атака закончилась на границе PCAP. Файлы 41 и 42 могут оказаться у разных worker и завершиться в обратном порядке.

Агент присваивает файлам (stream_id, sequence). В артефакте есть packet_index и capture timestamp. Reducer ждёт непрерывный готовый префикс файлов, затем сливает пакеты всех потоков домена по времени. Готовый файл 42 ждёт файл 41. Состояние TCP, IPv4-фрагментов и детекторов находится в общем checkpoint домена и не сбрасывается при смене файла/worker.

Reducer использует минимальную безопасную временную границу всех потоков домена — watermark. Пропавший файл, ошибка parser или незакрытый замолчавший поток удерживают эту границу. Это сохраняет полноту истории ценой задержки.

Что масштабируется¶

Роль Единица работы Параллелизм
API HTTP-запрос Один сервис API в поставляемом Compose
Parser Один PCAP N файлов параллельно, в том числе от одного агента
Detector/reducer Observation domain Один владелец домена; разные домены параллельно

Добавление detector-worker не ускоряет один горячий домен. Разделения внутри домена по целям/правилам пока нет. Kafka, object storage и отдельный flow-сервис не входят в текущую реализацию.

Домены и источники¶

Домен объединяет сенсоры с согласованными часами и неперекрывающейся видимостью. Это позволяет обнаружить DDoS от нескольких агентов. Если один пакет виден двум сенсорам, он будет учтён дважды: межсенсорной дедупликации нет. Домен не является границей tenant/RBAC: администратор панели видит всё.

Для исторического replay создают новый домен. Регистрация потока со временем раньше уже обработанной истории отвергается, чтобы не продолжить окна с пропущенными данными.

Восстановление¶

Задания имеют lease, heartbeat и generation. Прежний worker после потери lease не может зафиксировать результат. Parser публикует JSONL атомарным переименованием. Reducer одной транзакцией сохраняет checkpoint, курсоры, сигналы, инциденты и outbox. Повтор доставки sequence с тем же хешем идемпотентен; другой контент вызывает конфликт.

Это не распределённая транзакция между файловой системой и БД. Сбой между переименованием и commit может оставить неучтённый файл; автоматического сборщика таких файлов нет. Checkpoint использует внутренний pickle: запись в БД и volume считается административной привилегией.
