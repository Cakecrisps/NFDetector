# Эксплуатация

Команды ниже используют стандартный `compose.yaml`. Если установка запущена
с TLS/другими override, всегда передавайте тот же набор `-f`, `--env-file`
и имя проекта `-p`. Отсутствующий override способен изменить опубликованный
порт, сертификат, образ или mount. Не копируйте конфигурацию из `/tmp`
предыдущих сеансов в постоянную эксплуатацию.

## Наблюдение

```bash
docker compose ps
docker compose logs --tail=100 api lb parser-worker detector-worker
docker compose exec -T api python -m distributed --help
```

В панели проверяйте отдельно: связь агента, capture state, его локальную
очередь, ошибки файлов, последнюю временную метку домена и состояние workers.
`GET /health` проверяет API и подключение к БД, но не исправность полного
конвейера и не продвижение детектора.

Heartbeat агента отправляется примерно раз в 10 секунд при работающем цикле;
свежая связь — последняя минута. Данные о связи также обновляются при
аутентифицированных запросах. Отправка длительного файла или ошибки сети
могут задержать heartbeat. Это не сетевой ping и не счётчик capture drops.

На хосте автоматически установленного агента:

```bash
systemctl status nfagent
journalctl -u nfagent --since '1 hour ago'
du -sh /var/lib/nfagent/spool
df -h /var/lib/nfagent
```

## Диск и очистка

На агенте файлы собственного spool удаляются только после проверенного и
сохранённого ACK сервера. Загруженные вручную пользовательские файлы не удаляются.
В активном live manifest остаются неподтверждённые записи. При заполнении
spool захват останавливается; сохранённые файлы не перезаписываются.

На сервере **автоматической retention нет**: `captures/`, `parsed/`, таблицы
сигналов, инцидентов, outbox и audit растут. Квота 2 GiB на агента суммирует
все зарегистрированные PCAP, включая обработанные. После заполнения сервер
возвращает `429`, локальная очередь растёт до остановки захвата.

Ручное удаление файлов из `data` не является корректной очисткой: ссылки,
курсоры и квота в PostgreSQL останутся. Готовой безопасной команды purge нет.
До реализации retention используйте короткие сессии наблюдения, мониторинг
свободного места и расширение/архивирование хранилища по проверенному плану.
`docker compose down -v` уничтожает данные и не подходит для регулярной очистки.

## Обновление

1. Запишите версию кода, полный набор Compose-файлов и параметры запуска.
2. Сделайте согласованную резервную копию и проверьте возможность восстановления.
3. Сверьте версии checkpoint/правил: несовместимый checkpoint не продолжится.
4. Пересоберите сервисы с теми же override и требуемым числом workers.
5. Проверьте здоровье API, отсутствие ошибок доменов, поступление файлов и
   продвижение capture-времени. Сам `--wait` не проверяет workers без healthcheck.

```bash
docker compose up -d --build --scale parser-worker=3 --scale detector-worker=2 --wait
```

Схема БД инициализируется идемпотентно при запуске сервисов под advisory lock.
Это не полноценная система версионированных миграций с автоматическим rollback.
Изменение Python-кода состояния может потребовать отдельной миграции даже
при прежнем номере checkpoint. Совместимость должна быть проверена на копии БД.

NGINX разрешает адрес `api` при загрузке конфигурации. Если API пересоздан
отдельно и получил другой IP, перезагрузите конфигурацию работающего LB:

```bash
docker compose exec -T lb nginx -s reload
```

Для обновления сертификата с файловым bind mount пересоздайте LB по инструкции
[установки сервера](../getting-started/server.md). Агент с certificate pin
потребует обновления fingerprint, обычный режим `--ca` проверяет доверие иначе.

## Резервная копия и восстановление

Нужно сохранить PostgreSQL **и** volume `data` в согласованном состоянии.
Там лежат исходники, JSONL, setup-код и привязанные к ним курсоры.
Дополнительно сохраните правила, `ext/`, Compose override, приватный `.env`
и TLS-материалы с соответствующим контролем доступа.

Самый простой согласованный снимок требует окна остановки: корректно
остановить/доставить агентов, остановить API и workers, дождаться окончания
записи, затем сделать `pg_dump` и снимок `data`. PostgreSQL может работать
для выполнения `pg_dump`; не копируйте его открытый каталог как обычные файлы.
Штатного автоматизированного backup/restore скрипта в репозитории нет.

Восстанавливайте в отдельную установку с совместимой версией кода, теми же
внутренними путями и правилами. Проверьте соответствие PCAP/артефактов ссылкам,
health, checkpoints и ожидаемые инциденты на тестовой последовательности
до подключения рабочих агентов. Конкретный RPO/RTO ещё не измерен.

## Повторный анализ и исторические сигналы

Для новых правил создавайте агента в **отдельном replay-домене**, загружайте
PCAP в порядке захвата и закрывайте поток `/seal`. Это отделяет исторический
анализ от live watermark. Старую историю сохраняйте для сравнения.

Для объединения старых сигналов без пересчёта пакетов:

```bash
docker compose stop detector-worker
# Дождитесь окончания lease прежних reducer, по умолчанию до 60 секунд.
docker compose run --rm --no-deps api backfill-incidents --domain DOMAIN
docker compose up -d --no-deps detector-worker
```

Сохраняйте прежнее число реплик при запуске. Команда идемпотентна, сохраняет
исходные сигналы и не меняет checkpoint. Длительность ограничивается метками
исходных срабатываний; восстановление активности между ними требует replay PCAP.
Универсального безопасного редактирования checkpoint вручную не предусмотрено.
