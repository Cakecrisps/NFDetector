# Оценка модели и план работ

## Что даёт текущая архитектура

Полный PCAP на сервере сохраняет возможность расследовать сигнал и повторить
анализ под другими правилами. Агент остаётся простым: захват, надёжная доставка
и минимальные привилегии. Правила обновляются централизованно.

Разделение parser и reducer позволяет независимо распараллеливать тяжёлый
разбор файлов, сохраняя единые окна атак и TCP-состояние. PostgreSQL даёт
устойчивую очередь, lease/fencing и транзакционное сохранение результатов
без дополнительного брокера в небольшой установке.

Checkpoint и идемпотентная доставка позволяют пережить потерю ответа,
перезапуск worker и завершение файлов в обратном порядке. Инциденты объединяют
повторные сигналы, сохраняя первичные свидетельства для разбора.
Один внешний HTTPS-порт упрощает TLS и сетевую конфигурацию.

## Основные недостатки

| Недостаток | Практическое влияние |
| --- | --- |
| Полный трафик передаётся и хранится централизованно | Нагрузка на upload/диск, чувствительные данные в PCAP и JSONL |
| Retention отсутствует, quota считает всю историю | Длительное наблюдение неизбежно дойдёт до `429` и остановки захвата |
| Один reducer на домен, checkpoint целиком на каждый batch | Предел скорости горячего домена, CPU/DB I/O на сериализацию |
| Watermark зависит от самого медленного потока | Тихий/сломанный агент удерживает анализ здоровых |
| Parser сортирует файл в RAM и пишет hex-payload | Высокий RSS, усиление размера и дискового I/O |
| Пороговые эвристики и ограниченный L7 | Ложные срабатывания и слепые зоны шифрованного трафика |
| Один хост и общий volume | Нет HA, многосерверного хранения и проверенного disaster recovery |
| Pin привязан к конкретному сертификату | Ротация сертификата требует обновить доверие агентов |
| Схема через идемпотентный SQL, состояние pickle | Сложнее обновлять/откатывать модель состояния, DB должен быть доверенным |

При 100 Mbit/s непрерывного захваченного трафика это примерно 12.5 MB/s,
1.08 TB/сутки до накладных расходов. Очередь 2 GiB покрывает около 172 секунд.
Это расчёт ёмкости, а не замер пропускной способности NFDetector.

## Порядок следующих работ

| Приоритет | Задача | Критерий готовности |
| --- | --- | --- |
| P0 | Retention PCAP/JSONL/БД и уборка orphan-файлов | Не удаляются данные, нужные checkpoint/replay; quota освобождается согласованно; проверены crash/retry |
| P0 | Политика idle/offline потоков и observation gaps | Один умерший агент не останавливает всё бессрочно; потеря полноты явно видна; late data обрабатывается предсказуемо |
| P0 | Наблюдаемость и нагрузочный soak-test | Capture drops, возраст backlog, p95 capture→incident, RSS/CPU/IO/DB, свободный диск; определён проверенный предел нагрузки |
| P0 | Согласованный backup/restore и постоянный deployment-конфиг | Восстановление на чистом хосте из копии БД+файлов, измерены RPO/RTO |
| P1 | Доставщик incident outbox | Retry/backoff, дедупликация у получателя, отметки доставки, правила обновления/закрытия инцидента |
| P1 | Версионированные миграции БД/checkpoint и replay CLI | Проверяемое обновление/откат, dry-run, сравнение результатов |
| P1 | Управление доверием TLS и обновлением агентов | Ротация сертификата без ручного обхода всех хостов, подтверждённая версия пакета |
| P1 | Улучшение качества правил | Корпус benign/attack PCAP, точность/полнота; SSH с журналами sshd; C2 по новым соединениям |
| P2 | Shards внутри домена и общее хранилище | DDoS одной цели видит все источники; перенос состояния не теряет окна; несколько Docker-хостов |
| P2 | Перекрывающиеся сенсоры и временные расхождения | Явная модель дедупликации, late-data и согласованных часов |
| P2 | Роли и изоляция организаций | Ограниченные области просмотра/управления и проверенные границы доступа |

Это план, а не перечень скрыто включённых функций. Сначала стоит закрыть
хранение, остановки доменов и измерение предела нагрузки. Выбор другого брокера
сам по себе эти проблемы не решит.

Для shards ключ нужен по защищаемой цели/правилу, а не только по атакующему:
иначе источники одного DDoS разойдутся по состояниям. Состояние TCP должно
попадать к согласованному владельцу flow. Нужны перенос checkpoint, поколения
владельцев, сохранение порядка и тесты cross-shard корреляции.
