# Подключение агента

Сначала [установите сервер](server.md) и [смените первоначальный пароль](../guides/panel.md). Для обычного Linux-хоста используйте команду из панели; ручной запуск и загрузка PCAP описаны ниже.

## Автоматическая установка агента из панели

При создании агента заполните поле «Адрес панели со стороны агента»: IP или
DNS-имя панели, доступные с целевого хоста. Например, `192.168.122.1` превращается
в `https://192.168.122.1`; можно указать полный адрес с портом. Адрес сохраняется
для конкретного агента, используется в первой команде установки и при замене ключа.
После создания панель показывает готовую команду. Скопируйте её на
целевой Linux-хост с Python 3 и sudo. Поддержаны Debian/Ubuntu (`apt-get`) и
Fedora/RHEL (`dnf`), требуется работающий systemd. На хосте нужны доступ к
серверу, репозиториям ОС и PyPI. Постоянный ключ в команду не входит.

Если панель открыта на `localhost`, в форме создания укажите IP или DNS-имя,
доступное с целевого хоста. Для изменения адреса в готовом диалоге установки
отредактируйте поле и нажмите «Обновить команду».
Интерфейс выбирается по маршруту к серверу; можно явно указать нужный интерфейс.
Подсказку адреса в форме можно задать отдельно через `NF_AGENT_URL`,
например `https://192.168.122.1`; иначе используется адрес панели.
Трафик загрузки PCAP исключается из захвата. У существующего агента команда
доступна через «Установить»; она предназначена для одного хоста. Для второго
хоста создайте отдельного агента.

Команда содержит одноразовый код на 15 минут, SHA-256 сертификата LB и hash
установщика/пакета. Сертификат сверяется **до отправки кода или ключа**, файлы
сверяются до запуска. Самоподписанный сертификат поддерживается через явное
закрепление fingerprint, без доверия произвольному сертификату. Смена сертификата
LB требует обновить fingerprint уже установленных агентов; смена установщика
или пакета требует получить новую команду. Установленный агент продолжает
проверять fingerprint на каждом новом TLS-соединении. Альтернативный ручной
режим `--ca` сохраняет обычную проверку CA и имени сервера.

Создание новой команды отменяет предыдущую для того же агента. Отзыв или
замена ключа также отменяют код. При использовании кода сервер выдаёт новый
постоянный ключ и заменяет предыдущий, включая ручной ключ из диалога создания.
Секрет одноразового кода хранится в БД только как hash; постоянный ключ тоже
хранится как hash. Коды и ключи не передаются в URL и не пишутся в audit.
Команду из истории shell нельзя использовать повторно после её применения.

Установщик ставит dumpcap и Python-зависимости, создаёт пользователя `nfagent`,
приложение в `/opt/nfagent`, файлы `0600` в `/etc/nfagent`, очередь в
`/var/lib/nfagent` и службу `nfagent.service` с автозапуском. Служба работает
от `nfagent` с `CAP_NET_RAW`/`CAP_NET_ADMIN`, `NoNewPrivileges` и файловой системой
только для чтения за исключением каталога очереди. Существующая ручная установка
в `/opt/nfagent` автоматически не перезаписывается. Ошибка до обмена кода
позволяет повторить команду; после обмена получите новую команду или исправьте
службу через `systemctl restart nfagent`.

Проверка: `systemctl status nfagent` и `journalctl -u nfagent -f`. Установщик
проверяет запуск службы; состояние захвата и доставки смотрите в панели.
Защищаемые адреса по-прежнему настраиваются в `ext/protectips.txt`.

В Compose публичный сертификат копируется LB в отдельный `tls-public` volume;
API читает только его, приватный ключ остаётся на LB. При обновлении существующей
установки пересоберите и пересоздайте `api` и `lb`, чтобы подключить этот volume.
Для другого способа запуска задайте `NF_TLS_PUBLIC_CERT` с путём к публичному
сертификату внутри API-процесса.


## Ключ агента

Ключи можно создавать в разделе «Агенты» после входа и смены первоначального
пароля. Также доступна административная CLI внутри API-контейнера. Секрет не печатается в консоль, в PostgreSQL хранится
его SHA-256. Выданный файл имеет права `0600`.

```bash
docker compose exec -T api python -m distributed issue-key \
  --name sensor-1 --domain office --key-file /tmp/sensor-1.key
mkdir -p .local
docker compose cp api:/tmp/sensor-1.key .local/sensor-1.key
chmod 600 .local/sensor-1.key
```

Команда сообщает `agent_id`. Отзыв:

```bash
docker compose exec -T api python -m distributed revoke-key --agent-id AGENT_UUID
```

`domain` — единая история событий с согласованными часами. Несколько агентов
одного домена объединяются для DDoS и других правил. Используйте один домен
для сенсоров, наблюдающих неперекрывающиеся части трафика. Межсенсорная дедупликация
одного и того же пакета пока не реализована; повторная доставка одного файла
и повтор выполнения заданий дедуплицируются.

## Отправка существующих PCAP

Для ручного запуска скопируйте исходники проекта на агентскую машину. Нужен Python 3.10+ и агентские зависимости. В примере ключ уже сохранён на агенте:

```bash
python3 -m pip install -r requirements-agent.txt
python3 -m distributed upload \
  --server https://detector.example.com \
  --key-file .local/sensor-1.key \
  --state .local/upload-state.json --interface eth0 \
  capture-001.pcap capture-002.pcapng
```

Пути перечисляются в capture-порядке. Один state-файл — одна последовательность.
При обрыве повторите ту же команду: UUID потока, sequence и подтверждения
восстановятся с диска. Исходные пользовательские файлы не удаляются.
После доставки всей последовательности агент вызывает `/seal`.
Для независимого нового захвата используйте другой state-файл.

Для исторического захвата создавайте отдельный домен replay: добавление источника
с начальным временем ниже уже обработанного watermark отвергается явно.
Это предотвращает незаметную потерю старых событий.

## Live-агент

Дополнительно нужен `dumpcap` и разрешённый ему захват выбранного интерфейса
(на Debian/Ubuntu пакет `wireshark-common`). Агент запускается на сенсоре;
серверным контейнерам доступ к сетевым интерфейсам сенсора не нужен.

```bash
python3 -m distributed capture \
  --server https://detector.example.com \
  --key-file /etc/nfdetect/agent.key \
  --state /var/lib/nfdetect/agent-state.json \
  --spool /var/lib/nfdetect/spool --interface eth0 \
  --filter 'not (host SERVER_IP and tcp port 443)' \
  --quota-mib 2048
```

Замените `SERVER_IP` реальным адресом. Фильтр обязателен, чтобы не захватывать
собственную отправку PCAP. Предпочтителен отдельный интерфейс управления.

Захват непрерывный через один `dumpcap`, с ротацией по 2 секундам или 16 MiB.
Закрытые файлы попадают в устойчивый manifest; активный файл не отправляется.
Подтверждение проверяется по stream ID, sequence и SHA-256. Только после
сохранения подтверждения принадлежащий spool файл удаляется. Подтверждённые
записи удаляются из live-очереди, её размер не растёт со сроком работы агента.

Сначала агент регистрирует поток, затем начинает захват. При старте нужна связь
с сервером; уже работающий агент переживает обрывы через spool и повторы
с backoff/jitter. Ключевые/неустранимые ошибки сохраняют очередь и завершают агент.

Отдельный watchdog следит за квотой даже во время заблокированной отправки.
При заполнении spool захват останавливается с явной ошибкой, неподтверждённые
файлы не перезаписываются. После перезапуска старый epoch доставляется и
закрывается, затем регистрируется новый. Обрыв захвата не выдаётся за непрерывный
поток. Остановка Ctrl+C закрывает последний файл и пытается доставить очередь.
