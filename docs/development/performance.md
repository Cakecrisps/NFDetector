# Производительность детекторов

## Что изменено

Ранее каждый пакет добавлялся в несколько окон с полными объектами PyShark.
Затем каждое окно повторно обходилось целиком: извлекались IP/порты/флаги,
строились счётчики и сортировались временные метки. При N пакетах, попавших
в одно окно, это давало квадратичную работу.

`general/streaming.py` содержит независимое от PyShark потоковое ядро.
На вход поступает один словарь полей пакета и результат распознавания
аутентификации. Монитор извлекает их по одному разу на пакет.

- DDoS от одного IP, HTTP flood и brute force: очереди `(timestamp, key)`
  и счётчики. Удаление старого события уменьшает счётчик; полный обход не нужен.
- Распределённый DDoS: счётчики источников отдельно на защищаемый адрес.
  Список ведущих источников выбирается только при срабатывании.
- SYN flood: таблица ожидающих соединений и очередь истечения. Повторный SYN
  обновляет время соединения без увеличения числа соединений; SYN-ACK его убирает.
- C2: очереди временных меток и интервалов, текущая сумма интервалов,
  монотонные очереди для минимума и максимума. Сортировки и повторного обхода
  всех пакетов нет. Сохранена прежняя трактовка события как пакета пары IP;
  распознавание именно новых соединений остаётся отдельной задачей качества C2.
- Подозрительные IP: проверка множеств для текущего пакета.

Операции со счётчиками и очередями имеют амортизированную стоимость O(1)
на событие при фиксированном наборе правил. Истечение большой пачки старых
событий может задержать один следующий пакет, но каждое событие удаляется
один раз. Выбор ведущих источников при DDoS-срабатывании зависит от числа
источников, поэтому весь конвейер нельзя объявлять строго O(1).

Из RAM детекторов убраны объекты пакетов: хранятся только ключи и временные
метки в пределах окон. Объём состояния всё ещё зависит от числа пакетов и
уникальных соединений в окне, а не является фиксированным лимитом RAM.

PCAP теперь декодируется одним проходом с `keep_packets=False`; предварительный
проход ради количества пакетов убран. Вместо процента прогресса выводятся
обработанное количество и текущая скорость. Захват закрывается и при ошибке.

## Замер

Воспроизводимый микробенчмарк:

```bash
python -m benchmarks.detectors --counts 500 1000 2000 --repeat 3
```

Повторный замер 25 октября 2026 года: Python 3.12, медиана трёх запусков.
Команда выполнена при проверке документации; это микробенчмарк ядра.

| Пакетов в окне | Повторный обход окна, с | Потоковый вариант, с |
| ---: | ---: | ---: |
| 500 | 0.25020 | 0.00189 |
| 1000 | 0.93696 | 0.00358 |
| 2000 | 3.76893 | 0.00785 |

Измеряется один включённый DDoS-детектор на искусственных уже декодированных
пакетах. Для обоих вариантов учитывается извлечение полей; у потокового это
происходит один раз, у старого — при каждом обходе. Все пакеты остаются в одном
секундном окне, порог выше их числа, вывода уведомлений нет.

На 2000 пакетах в этом сценарии получилось около 480×, но это **не** ускорение
всего приложения и **не** оценка пропускной способности сетевого захвата.
TShark, PCAP I/O, все правила вместе, формирование отчётов и HTTP-уведомления
в замер не входят. Абсолютные цифры зависят от машины и версии интерпретатора.

## Поведение и границы

- Окна привязаны к времени пакетов, включая граничную метку `now - window`.
  Скорость чтения PCAP на результат не влияет.
- Rate/SYN/C2-оповещения выдаются при переходе к состоянию атаки; одинаковая
  продолжающаяся атака не пишет новое уведомление на каждый пакет. После спада
  состояния новое пересечение порога снова вызывает оповещение. Проверки
  подозрительных IP остаются событиями каждого пакета.
- Счётчики rate/SYN ведутся по источнику **и цели**: трафик к разным защищаемым
  адресам не склеивается, оповещение содержит соответствующую цель.
- В потоковом `analyzer.stats.total` пакет учитывается один раз, вместо повторного
  подсчёта при каждом обходе каждого правила. Старые batch-методы сохранены для
  совместимости и прямых вызовов; локальный монитор их на каждом пакете не вызывает.
- Один экземпляр ядра обслуживает один упорядоченный поток. Текущее ядро отвергает
  убывающие timestamps до изменения своего состояния. Для смешанных/неупорядоченных
  захватов нужен адаптер переупорядочивания, реализованный в серверном reducer.
- Один экземпляр монитора сохраняет состояние между последовательными вызовами
  `analyze_file`, так что окно может пересекать границу файлов. Новый экземпляр
  начинает независимый поток; сервер должен управлять этим явно.

## Что ещё ограничивает скорость

Локальный режим использует PyShark/TShark и хранит часть отчётных данных в RAM
(`http_endp`, список оповещений, уникальные адреса и домены). Внешние HTTP-логи
отправляются синхронно. Эти затраты не входят в микробенчмарк.

Серверный режим использует dpkt, а не TShark. Parser держит события файла
в RAM, сортирует и записывает JSONL с hex-payload. Один reducer на домен
восстанавливает и сериализует полный checkpoint на каждом batch; это может
стать узким местом раньше parser. Дополнительные detector-worker ускоряют
разные домены, но не один горячий домен.

Сквозной предел packets/s, длительный RSS и p95 capture→incident пока не
установлены. Нужно измерять раздельно захват/drops, upload, parser, reducer,
DB I/O, размер checkpoint, возраст backlog и диск. Повышение порогов правил
меняет чувствительность, но не является проверенной оптимизацией производительности.

Полный анализ и следующие шаги — в [оценке модели](../project/assessment.md).
